# Engineering log

Full phase-by-phase build log for [Call Scorer](./README.md), kept as it was written during the build - what was tried, what broke, how each fix was actually verified. Moved out of the main README to keep that scannable; this is the detail behind its "Architecture & key decisions" summary.

### Loom quick reference - strongest stories to tell, jump to the full writeup

- **A documented approach didn't work, and here's the investigation, not just the pivot.** Anthropic's own recommended structured-output mechanism (`output_config.format`) reliably failed server-side on this schema. Tried it, hit a 400, reproduced it a second time to rule out a fluke, then switched to a forced tool call + client-side Zod validation instead - and can explain *why* that's not a downgrade. → Phase 2, bullet 1.
- **A real bug the test fixtures caught before it shipped**, not after: "the one thing" simulator was comparing a dimension's raw Stage-2 score against its max instead of the capped/reported score - would have hidden the single highest-leverage fix on a call. → Phase 1 commit / conversation, the `computeOneThing` currentScore fix.
- **Found and fixed a real inconsistency in the client's own rubric document** (coaching's 12 dimensions sum to 105, not the 100 its own scope note claims) - a concrete example of not treating a source spec as gospel, deriving the correct behavior instead of guessing which number was right. → Phase 1, bullet 1.
- **A full failure-mode spec for evidence validation, decided in writing before any code**, specifically including the tempting shortcut *not* taken: a real quote cited at the wrong line does NOT get silently relocated to wherever it actually matches, because that would mean the pipeline fixing the model's own citation error instead of catching it. → Phase 3, bullet 1.
- **Used the evidence validator to root-cause a real failure instead of loosening the validator to pass it.** One transcript tripped the fail threshold; all 8 invalid citations traced to one exact pattern (the model ellipsis-joining two real-but-separate parts of a long line); fixed the prompt at the source, regenerated, watched the invalid rate fall from 21.6% to 0% on that transcript and 7.9%→2.1% in aggregate. Real before/after numbers, not a claimed fix. → Phase 3, bullets 5-7.
- **A reasoned, asymmetric threshold policy, argued through instead of picked arbitrarily** - warn cheaply and sensitively (doesn't stop anything), fail conservatively and only on both a rate AND an absolute-count floor (stops the run, so it needs to resist small-sample noise). → Phase 3, bullet 3.
- **A two-phase-later payoff from a Phase 2 trade-off - the best "this is why investigating matters" story in the project.** Giving up strict/grammar-constrained structured output in Phase 2 (it was timing out) meant accepting a non-strict tool call that only guides the model instead of hard-constraining it. Two phases later, that exact trade-off surfaced concretely: Stage 2's `dimensions` field came back as a malformed, non-re-parseable string 3 of 4 times on the most evidence-dense real transcript. Not a new, unrelated bug - the other half of a decision already made and documented. Mitigated two ways at once (retry count sized from the measured failure rate, not guessed; a prompt change that improves both reliability AND report quality), and proven live: one real run failed on attempt 1 and self-healed on attempt 2, logged, not hidden. → Phase 4, bullets 5-6.
- **The score-clamp safety net caught something a human grader might plausibly have wanted to do.** Real Stage 2 output scored a dimension 9/10 on a rubric where the only legal values are {0, 3, 7, 10} - a reasonable "almost perfect" instinct that this specific rubric doesn't allow. Caught, clamped, visibly flagged - not silently accepted, not silently overwritten with no trace. → Phase 4, bullet 3.
- **Checked a "did I just break something" moment instead of assuming it was fine.** Ran the real schema migration against the live Supabase project, had a beat of "oh shit i ran the whole file" panic - instead of guessing, ran 3 read-only introspection queries against the actual database (columns, RLS status, policies) and confirmed everything landed exactly right. `db/schema.sql` turned out to be fully idempotent by design, but verified that rather than assumed it. → Phase 6, bullet 1.
- **Proved "a failed run says why" by causing a real failure, not a mocked one.** Temporarily pointed the model config at a model id that doesn't exist, restarted the dev server, and submitted a real transcript through the real API - watched the actual Anthropic 404 propagate all the way through the background pipeline to `status: 'failed'` with the real error text rendered on the run page. Also noticed and can explain why that error correctly skipped the 3-attempt retry loop: retries exist for transient generation issues, not a guaranteed-every-time rejection. → Phase 6, bullet 6.
- **The strongest bug story in the project: a system built to distrust the model caught the model contradicting itself.** A late, purely presentational addition (the synthesis call, which isn't allowed to change any score) restated two facts from the SAME Stage 1 response side by side - and they disagreed. D10's own cited, validated evidence proved a live booking; the separate, unevidenced call-level signal said the opposite; nothing had ever cross-checked the two, so a cap fired on the wrong one and zeroed a real 5/5. Root-caused, then fixed with a rule that only trusts Phase 3's *validated* evidence to resolve the conflict - never the bare boolean - so the fix doesn't quietly introduce the same "trust an unevidenced claim" failure it exists to close. Deliberately scoped to the one pairing that's provably safe, not generalized on a guess. Reproduced the original failure 3/4 times, reproduced the fix working live (not just in a unit test) on a fresh run after landing it. → Phase 5, bullets 3-5.
- **A UI bug that turned out to already be poisoning the model's own prose, caught by testing the first real render instead of trusting the type-checker.** The report banner showed "100 / 90" - two genuinely different scales (`total` is always /100; `maxPossible` is the pre-rescale raw-points denominator) divided as one fraction. Tracing where else that same fraction got built found it already baked into the synthesis call's prompt input since Phase 5 - meaning every coaching-call brief's own generated sentence had been silently saying nonsense like "100/90" the whole time, not just this new UI. Fixed both call sites, re-ran the real pipeline to confirm the brief text itself changed, not just the display. → Phase 7, bullets 2-3.
- **A silent rendering bug that only a human eye on the actual output would ever catch.** The PDF's "one thing" card printed `"3 '5"` where it should've said `"3 → 5"` - the standard PDF font's encoding simply doesn't contain that arrow glyph, so it drew a wrong character instead of throwing. `tsc`, `eslint`, and a successful build all had nothing to say about it; only rasterizing the actual PDF and reading the pixels caught it. → Phase 8, bullet 3.
- **Closed a failure path by asking "what if the thing that records the failure also fails?"** Every prior failure-handling story in this project (Phase 6's forced 404, Phase 9 below) assumed the `failRun()` write itself always succeeds. It's a network call to Supabase and can fail too - and if it does, the old code turned that into a silent unhandled rejection with the run stuck forever and nothing written anywhere. Fixed with a nested try/catch plus a broadened stalled-run definition (`'pending'`, not just `'running'`) as the backstop for the case even the fix itself can't recover from. Explicitly flagged that this one is verified by code review, not a live-forced reproduction like the others - can speak to why that's a real distinction, not just a hedge. → Phase 9, bullets 4-5.
- **The best "local testing has a ceiling" story in the project: a bug that only exists on the real platform, found the first time the real platform was actually used.** `maxDuration = 60` had survived 4 phases of extensive local testing untouched, reasoned as "safe" but never pressure-tested - because `next dev` has no equivalent hard per-request kill switch to trip. The very first live production run that needed a retry got killed outright by Vercel's real enforcement, confirmed via `vercel logs`: `Task timed out after 60 seconds`. Fixed (180s), redeployed, and reverified against the exact same failing transcript on the fixed deployment - completed correctly this time, matching the established baseline. Also deliberately left the killed run in place afterward rather than cleaning it up, as a live demonstration that the Phase 6 staleness backstop actually catches this exact scenario end to end, not just in theory. → Phase 10, bullets 3-5.

### Phase 1 - rubric contracts + deterministic scoring

- **Coaching rubric point-total discrepancy.** The coaching rubric's own scope note claims totals of 100 (D4 active) / 85 (D4 disabled), but its 12 dimensions' own stated point values sum to 105 - verified against the source file directly, not a transcription error. 105 minus D4's 15 is 90, not 85 either. Resolved by deriving `maxPossible` from the sum of the dimensions actually being scored, rather than trusting the rubric's stated totals - so a perfect call always lands at exactly 100/100, and the D4-disabled denominator is a derived 90, not the rubric's stated 85. See `src/rubrics/coaching.ts` and `src/scoring/applyRubricRules.ts`.
- **D2 (Diagnostics Review) redistribution rule left out of scope.** The rubric says when D2 doesn't apply (non-milestone call, no video), "redistribute weight to D3 and D4" - a second, differently-shaped rescale on top of D4's. Deliberately not implemented; D2 is scored normally always, and its Fail/Surface bands naturally cover "no diagnostics happened this call."
- **"The one thing" is computed in code, not asked of the model.** Simulates raising each dimension to its rubric max (lifting any cap that was specifically constraining that same dimension, since maxing it out is logically inconsistent with the cap's own trigger condition still being true), recomputes the total via the same deterministic path used for real scoring, and picks the largest delta. The model only ever writes the explanatory sentence for whichever dimension the code already picked.
- **Caps, totals, and bands are 100% deterministic code**, not LLM judgment - both rubrics define their automatic-cap tables as hard rules, so a shared `applyCaps()` engine (behind rubric-specific `applyKickoffCaps()`/`applyCoachingCaps()` entry points) applies them the same way every run, rather than trusting a model to remember to self-apply them consistently.

### Phase 2 - Stage 1 evidence extraction

- **`client.messages.parse` + `output_config.format` (Anthropic's structured-output / constrained-decoding path) does not work for this schema.** Tried it first, since it's the documented "recommended" approach. It consistently failed server-side with `400 Grammar compilation timed out` on the Stage 1 schema's nested arrays (`dimensions[].evidence[]`) - reproduced twice against a real transcript, not a one-off. Switched to a forced (non-strict) tool call instead: `tool_choice: {type: "tool", name: ...}`, then validated the returned tool input against the same Zod schema (`Stage1OutputSchema.safeParse`) client-side. This keeps the schema-enforcement guarantee without depending on the grammar compiler that was timing out - the tradeoff is losing the server-side "guaranteed to validate" promise, in exchange for something that actually completes reliably. See `src/pipeline/stage1.ts`.
- **The evidence-extraction tool schema is built per rubric, not shared.** A first version statically listed every call-level signal from both rubrics in one schema. On a real kickoff call, the model filled in several coaching-only signals nobody asked about, because the tool schema offered them as available fields even though the system prompt correctly scoped to kickoff's 4 signals - the schema, not the prose, is what the model was actually following. Harmless downstream today (unused keys get ignored), but a real discipline gap, closed by generating the tool's signal properties from `rubric.automaticCaps` instead of a hardcoded union.
- **Stage 1's prompt deliberately withholds each dimension's scoring bands/criteria/point values** - only `whatToLookFor` + positive/negative signals are shown. Stage 1's only job is "what happened, cite the lines"; showing it the scoring scale risks anchoring its observations toward a score before Stage 2 (a separate call, working only from Stage 1's evidence) ever gets a turn to judge.
- **Known limitation: transcript format is assumed, not validated.** `indexTranscript()` treats every non-blank line as one speaking turn and doesn't check for the `[Speaker]: text` shape. Validated only against the exercise's own transcript format. A turn wrapped across multiple lines degrades citation granularity; a transcript with no line breaks at all would collapse every citation to "line 1," breaking the evidence-verification mechanism; a structured format (VTT/SRT, a platform's JSON export) isn't handled at all. No format-detection/normalization was built - deliberately out of scope given the exercise supplies exactly one format.
- **`insufficientEvidence: true` (the "I genuinely have nothing to judge this on" signal) has not yet been observed firing on real data.** Ran all 4 real transcripts; on every one, every dimension had at least something to cite - including cases correctly reported as `observed: false` backed by real evidence that the behavior explicitly didn't happen (e.g. coaching-02's coach saying outright "today isn't about screen-sharing footage"). That's a different, already-proven code path from "nothing at all to go on." Not a known bug - just an untested path, worth being precise about rather than over-claiming.

### Phase 3 - evidence validator

- **Failure-mode spec decided before writing any code:** a quote that doesn't match its cited line, a cited line that doesn't exist, and a quote that's real text but at the WRONG line, all fail the citation - none get silently corrected or relocated. In particular, a real quote found elsewhere in the transcript is NOT auto-relocated to where it actually matches; that would mean the pipeline fixing the model's citation for it, hiding a real reliability signal. The actual location (if found anywhere) is recorded as a diagnostic only, never used to pass the citation. Normalization is limited to whitespace collapsing and smart-quote flattening - no fuzzy matching, no partial-word matching, no edit-distance tolerance.
- **Zero valid evidence forces `insufficientEvidence: true`** for that dimension before Stage 2 ever sees it, even if Stage 1 claimed otherwise - this is the mechanism that makes "evidence or nothing" real rather than a prompt-only promise.
- **Warn/fail thresholds are asymmetric on purpose:** warning fires on `rate >= 8% OR count >= 3` (cheap, so sensitive); fail requires `rate >= 20% AND count >= 5` (expensive - stops the run - so conservative and gated on both a rate AND an absolute-count floor, so a couple of citations on a thin-evidence call can't fail a run on noise alone). Provisional, reasoned defaults - see `src/config.ts`.
- **Sanity-checked against all 4 real Stage 1 outputs, no new API cost** (`npm run validate` re-checks saved `dev-output/` JSON against the real transcripts). First pass: 3 of 4 transcripts came back at 2-6% invalid (comfortably under warning); kickoff-01 came back at 21.6% (8/37) - both thresholds tripped.
- **Root-caused the one fail case instead of adjusting the thresholds to hide it.** All 8 of kickoff-01's invalid citations were the exact same pattern: the model quoting a real opening clause and a real closing clause of one long, run-on transcript line, joined with "..." while skipping real content in between - technically-real words, wrong claim about being one continuous excerpt. Fixed at the source (the Stage 1 prompt now explicitly requires continuous quotes and tells the model to report two separate evidence entries instead of ellipsis-joining two parts of the same line) rather than loosening the validator to tolerate it, which would have been exactly the "silently normalize bad evidence" this validator exists to prevent.
- **Result after the fix, regenerating all 4 transcripts:** aggregate invalid rate dropped from 7.9% (12/151) to 2.1% (3/140); kickoff-01 went from 8 invalid to 0. Two ellipsis-joined citations survived regeneration on the other two transcripts (same lines as before a rerun) - expected, since the model isn't deterministic and one prompt instruction reduces a tendency, it doesn't guarantee zero occurrences. All 4 transcripts now sit comfortably under both thresholds; chasing full elimination of a residual ~2% stochastic pattern wasn't judged worth further iteration.

### Phase 4 - Stage 2 scoring, wired into the deterministic engine

- **Stage 2 gets the opposite information cut from Stage 1 on purpose.** Full bands, point values, and calibration notes this time (judging IS its job) - but never the raw transcript, only the validated `{line, quote}` evidence that survived Phase 3. If Stage 2 could see the transcript directly it could quietly score off things Stage 1 never cited, breaking the evidence chain Phase 3 exists to enforce.
- **A dimension with `insufficientEvidence: true` is still sent to Stage 2, not skipped.** Both rubrics' own principle is "score conservatively within the band on missing evidence," not "automatic zero" - Stage 2 is told explicitly when evidence is thin/absent and instructed to score the defensible low end, not invent behavior to fill the gap.
- **An illegal score gets clamped to the nearest real band value - visibly, never silently** (`scoring/scoreValidation.ts`). Proven on real data, not just a synthetic case: kickoff-02's Stage 2 call returned 9 for D9, a dimension whose bands are strictly {0, 3, 7, 10} with no value in between - a plausible "just short of perfect" human instinct that the rubric genuinely doesn't allow there. Clamped to 10, flagged with `scoreClampReason` on the report, not overwritten with no trace.
  - **"Clamped" doesn't mean the same thing for every dimension - it depends entirely on that dimension's own band shape, not one blanket rule.** Three distinct cases: (1) a genuine range (e.g. kickoff D1: Strong 6-8) - any value inside it, like 7, is legal and untouched, no clamping; (2) a fixed-value dimension (e.g. kickoff D9: 10/7/3/0 only, and every coaching dimension - "discrete only, no interpolation" per the rubric's own text) - there is no legal in-between at all, so a 9 isn't "close to Elite," it's simply not a value this dimension can take, and gets clamped; (3) a genuine gap between two real ranges on a handful of small kickoff dimensions (D3's bands are 4.5-5 and 2.5-3.5 - nothing covers 4.0, confirmed against the source rubric file directly, not an encoding slip) - also clamped, for a different reason than case 2. The validator doesn't special-case these three - it's the same "does this score fall inside ANY defined band" check either way, but worth being precise that "clamped" covers genuinely different situations underneath.
- **Found and fixed the same precision gap in `cappedBy` that Phase 3 found in evidence citations - reported adjustments that didn't actually adjust anything.** `capEngine.ts`'s `maxDimension` effect was flagging a dimension as `cappedBy` whenever the cap's CONDITION was true, even when the cap's ceiling never actually bound (e.g. D4 independently scored 5 by Stage 2, already below the no-North-Star cap's ceiling of 10 - the cap fired in `appliedCaps` correctly, but showing `cappedBy` too would falsely tell a coach they lost points to a rule that made no numeric difference). Fixed to only record `cappedBy` when the cap's value actually changed the score; caught by inspecting a real pipeline run's output, not by code review, and locked in with a regression test.
- **A real, reproducible reliability issue - the other side of a trade-off already made in Phase 2.** Dropping strict/grammar-constrained structured output (`output_config.format`) back in Phase 2 because it was timing out meant accepting a non-strict forced tool call instead - which doesn't hard-constrain generation, it just guides it. On kickoff-01 (the most evidence-dense transcript, so the longest/most complex single Stage 2 response), this showed up concretely: `dimensions` came back as a STRING 3 of 4 times in direct reproduction - and critically, that string wasn't just double-JSON-encoded (re-parsing it as JSON also failed, truncated mid-generation), so there was no safe unwrap-and-accept fix available. This is a generation-reliability failure on a large/complex payload, not a validator bug and not fixable by prompt wording alone.
- **Mitigated two ways, not one:** (1) `callToolWithRetry` (shared by both stages) bumped from a single retry to 3 total attempts, sized from the measured failure rate, not guessed - proven live on coaching-02, where attempt 1 failed with the identical malformation and attempt 2 succeeded, transparently logged, not hidden; (2) Stage 2's prompt now asks for reasoning in 1-3 sentences instead of unbounded paragraphs, which shrinks the payload (less to generate correctly in one shot) and reads better in the report either way - a fix that helps reliability and quality at the same time, not a trade-off between them.
- **Validated end-to-end against all 4 real transcripts** (first time any transcript went all the way from paste to an actual total + band): kickoff-01 98.0/100 Elite (no caps), coaching-01 100.0/105 Elite (no caps, no one-thing candidate - the nullable-`oneThing` edge case, exercised for real), kickoff-02 66.0/100 At Risk (no-North-Star cap fired, D9 score clamped), coaching-02 96.7/90 Elite (D4 correctly disabled and rescaled, one retry needed and succeeded). The D4-max-lifts-its-own-cap oneThing math checked out exactly on a real scored call: kickoff-02's total moved from 66.0 to a projected 76.0 when D4 was hypothetically maxed, exactly `66 + (15-5)` - confirming the hypothetical correctly lifts the cap it's tied to on real, not just fixture, data.

### Phase 5 - synthesis call (brief, red flags, one-thing explanation)

- **Strictly downstream of everything deterministic, by design.** The synthesis call runs after Stage 2, score-validation, `applyRubricRules`, and `computeOneThing` are all finished - it's fed the already-final per-dimension `{score, maxScore, reasoning, quickFix, cappedBy, scoreClampReason}`, the already-final totals/band/caps, and the already-selected `oneThing` candidate. It never sees the raw transcript or Stage 1's raw evidence quotes, and the prompt states repeatedly that it cannot choose, score, cap, or reinterpret anything - only write prose describing numbers that are already locked in. See `src/pipeline/synthesis.ts`.
- **Bug: `redFlags` came back as an XML-tag string instead of a JSON array, reliably, whenever there were enough of them.** kickoff-01 (1 red flag) worked first try; kickoff-02 (5-6 red flags) failed the schema 3/3 times in direct reproduction, every time with the same shape - `"\n<item>...</item>\n<item>...</item>\n..."` as a single string, not a real array. Same family as Phase 4's Stage 2 malformation (a non-strict tool call only guides generation, it doesn't hard-constrain it), a different manifestation of it - the model reached for its default multi-item list style instead of the tool's array schema once the list got long enough. Fixed with an explicit, repeated instruction (schema property description AND system prompt) that `redFlags` must be a real JSON array with one string per element, never XML tags, never one joined string. Verified 3/3 clean on kickoff-02 after the fix; the retry safety net still caught and self-healed one more live recurrence on a later run, proving both layers (prompt fix + retry) are doing real work, not just the first one.
- **Bug: a Stage 1 self-contradiction, only surfaced because the synthesis call reports data faithfully instead of picking a side.** On coaching-02, D10's own evidence/observedBehaviour (cited, and validated against the transcript by Phase 3) plainly showed the next call being booked live - but the *separate* call-level `signals.nextCallBookedLive` boolean, from that same Stage 1 response, came back `false`. Nothing previously cross-checked the two, so the `next-call-not-booked-live` cap fired on the unevidenced half of Stage 1's own output and zeroed D10 (5/5 -> 0/5), which is why coaching-02 first reported 92.2/100 instead of what it should score with D10 credited correctly. This wasn't a Phase 5 bug - synthesis did exactly its job (faithfully restate both facts side by side in the brief), which is *how* it got caught; it's a pre-existing Stage 1 reliability gap from Phase 1-4 that Phase 5 happened to expose. Given the exercise README's own line - "one of the four transcripts exists to catch a system that guesses" - this is plausibly (not provably) that transcript.
- **Fixed two ways, deliberately, not one:** (1) a self-consistency instruction added to Stage 1's own prompt (`stage1Prompt.ts`) - cheap, reduces the base rate, same category as every other prompt-tightening fix in this project; (2) a new deterministic module, `src/pipeline/signalConsistency.ts`, that cross-checks a signal against its paired dimension and corrects the signal when they disagree - but trusts only the dimension's Phase-3-*validated* evidence to do the overriding, never a bare/unvalidated `observed` flag, so the fix doesn't itself introduce a new instance of "unevidenced claim wins." Every correction is recorded as a `SignalCorrection` on the `Report` (`signalCorrections: []` when nothing needed fixing) - visible, not silent, the same principle as `cappedBy` and `scoreClampReason`.
- **Deliberately scoped to exactly one pairing, not generalized.** Only `nextCallBookedLive` <-> `D10` is wired up, because D10's own rubric text calls it out as "binary dimension, no partial credit band" - the signal and the dimension are provably the same fact. Other signals were explicitly considered and rejected: e.g. kickoff's `noNorthStarStatement` vs `D4` is NOT a safe pairing, because D4 is a graded dimension where evidence existing (a goal conversation happened) doesn't imply a proper North Star was actually built - trying to auto-correct that pairing risks "fixing" a signal that was actually right.
- **Verified live, more than once, not just against fixtures.** Direct reproduction against coaching-02's real Stage 2 input hit the D10 contradiction 3/4 times before the fix. After both fixes landed, ran coaching-02 three more times: one run was internally consistent on its own (prompt fix alone sufficient, `signalCorrections: []`), one run reproduced the exact same contradiction live and the deterministic layer caught and corrected it (`signalCorrections` recorded the real cited evidence, e.g. line 313's booking confirmation, as the reason), and one run was clean again. D10 scored the correct 5/5 in all three post-fix runs; totals moved from a broken 92.2/100 to a correct 96.7 (twice) / 94.4 depending on the rest of that run's variance. Re-ran kickoff-01, kickoff-02, and coaching-01 afterward too, since the Stage 1 prompt change applies to every call type, not just coaching - all three matched their established baselines, no regression.

### Ahead of Phase 6 - transcript dedup, deliberately partial

- **Prompted by a fair question: is any of Phase 1's rubric/scoring code being wastefully recomputed per run, and should it be cached?** Answer, precisely: no - `kickoffRubric`/`coachingRubric` are plain module-level constants, loaded and cached once per server process by Node's own module system, and the scoring functions are sub-millisecond synchronous math over 12 dimensions. Nothing there is expensive enough to cache. The entire real cost per run (~$0.10, ~60-90s) is Stages 1 and 2's API calls, and those can't be cached in the normal sense - every transcript is different content the model has never scored before.
- **The one legitimate caching case: a byte-identical transcript submitted twice** (accidental double-submit, a literal re-paste) - worth detecting before paying for a second full pipeline run. Added `src/lib/transcriptHash.ts` (sha256 of `callType:transcript`, strict duplicate detection only - a single character difference hashes differently, only outer whitespace is trimmed) plus a `transcript_hash` column + index on `db/schema.sql`, so Phase 6 doesn't have to revisit the schema later.
- **Deliberately stopped there.** The actual "look up this hash, skip re-running if a completed report already exists" check has to live in the create-run flow against the real `runs` table - which doesn't exist in Supabase yet (Phase 6 hasn't started; `db/schema.sql` has never actually been applied). Wiring the lookup logic in now, before there's a table to verify it against, would mean building on infrastructure that doesn't exist rather than something tested end to end - the hash utility and schema are ready, the actual dedup check is one `SELECT` inside Phase 6's `POST /api/runs`, not before.

### Phase 6 - persistence + async

- **Schema applied to the real Supabase project, verified rather than assumed.** A moment of "oh shit i ran the whole file" turned out to be a non-event - `db/schema.sql` is entirely idempotent (`create table if not exists`, `create index if not exists`, an RLS-enable + trigger-recreate that are no-ops if already applied) with nothing destructive in it. Instead of taking that on faith, ran 3 read-only introspection queries against the live project (columns, `relrowsecurity`, `pg_policies`) and confirmed all 11 expected columns, RLS on, and zero stray policies - the anon key genuinely cannot touch this table. Worth having actually checked rather than assumed, given the RLS design's entire security argument rests on "no policies."
- **`after()` (Next.js), not a queue service, for background execution** - the response to `POST /api/runs` returns the run's id in ~2s, before the pipeline has even started; the actual 60-105s of work runs server-side afterward, which is what makes "I can close the tab, the evaluation keeps running" literally true. Considered and rejected a multi-step job-queue architecture (chaining short function calls to dodge Vercel's serverless duration cap) as overbuilt for this exercise - instead sized `maxDuration` conservatively and added a read-time staleness check instead (see next bullet), which handles the one real risk without the extra infrastructure.
- **A run stuck on `status: 'running'` with no update for 5+ minutes is treated as stalled, not left to spin forever.** This is the backstop for the one failure mode that isn't a clean thrown error: the background function itself getting killed mid-run by a platform duration cap, which would otherwise leave a row silently stuck with nothing to tell a reviewer why. Computed at read time (`RUN_STALE_MS` in `config.ts`) against `updated_at` - no cron job needed.
- **The transcript-dedup check (deferred from the "ahead of Phase 6" note) matches `pending`/`running`/`complete`, not just `complete`.** Broader than the original plan: the most likely real double-submit is re-pasting the same transcript while the first run is still mid-pipeline, not after it's already finished - a `complete`-only check would miss that case entirely. A prior `failed` run does NOT match, so a genuine retry after a failure always gets a fresh run rather than being stuck pointing at the failure.
- **Progress visibility was flagged as a gap and built in properly, not bolted on.** The user asked specifically for backend-status visibility and a step-by-step progress indicator. Added a `stage` column (`extracting_evidence` / `scoring` / `summarizing` - the three real LLM calls, not the sub-millisecond deterministic steps) and an optional `onStageChange` hook on `runScoringPipeline()` that the API route wires to a Supabase write at each stage boundary. The run page polls `GET /api/runs/[id]` every 2s and renders the live stage as a 3-step indicator - proven live, not just in code: watched a real submission through the actual browser advance `extracting_evidence -> scoring -> summarizing -> complete` in real time via the polling endpoint's logged requests.
- **Verified live in the browser end to end, not just via `npm run build` succeeding.** Ran the real dev server, pasted kickoff-01's actual transcript into the actual home page (loaded via `fetch` from `public/`, not retyped, to avoid any transcription risk), submitted it, watched the progress indicator advance through all 3 real stages, and landed on **98/100 Elite** - matching the earlier CLI-only baseline exactly. Hard-reloaded the run's URL fresh afterward and got back the identical complete report from Supabase, not cached client state - the actual "shareable, persistent URL" requirement, proven, not assumed. Resubmitting the identical transcript correctly returned `deduped: true` pointing at the same run id, no second pipeline run triggered.

### Phase 8 - PDF export

- **On-demand generation from the stored report, not a pre-built file.** `GET /api/runs/[id]/pdf` (`src/app/api/runs/[id]/pdf/route.tsx`) loads the run, requires `status: complete`, and calls `@react-pdf/renderer`'s `renderToBuffer` against `ReportDocument` right there in the request handler - streamed back with `Content-Type: application/pdf` and a `Content-Disposition: attachment` filename. No caching layer, no background job; the whole thing is cheap enough (sub-2s for a 12-dimension report) that generating fresh every download is simpler than inventing a cache-invalidation story for something that never changes once a run is complete.
- **`ReportDocument.tsx` is the third consumer of the one `Report` shape, not a new one.** Same principle `types/report.ts` states outright ("one shape, two renderers") - extended to three: `ReportView` (web), `ReportDocument` (PDF), and the Supabase `report` jsonb column itself are all the same data, just rendered differently. - **Bug, found by actually looking at a rendered page, not by the type-checker or a passing build.** The "one thing to improve" card printed `"3 '5"` instead of `"3 → 5"` - a literal U+2192 arrow silently rendered as a garbage glyph. Fixed by switching to the same ASCII `->` convention already used everywhere else in this codebase's prose (curly quotes, the middot, and the em dash all stayed as-is since those genuinely are in WinAnsi and render correctly - confirmed on the same page, in real transcript-quote text). A reminder that "renders without crashing" and "renders correctly" are different claims, worth checking separately for anything text-heavy.
- **Verified against two real, structurally different completed reports, not one.** Rendered a coaching call with D4 disabled and no `oneThing` (already maxed) - confirmed the score banner, red-flags card, and all 12 dimension blocks (including the disabled one's `disabledReason`) paginate cleanly across 5 pages with `wrap={false}` correctly keeping each dimension block intact rather than splitting across a page break. Rendered a kickoff call *with* a real `oneThing` candidate - confirmed that card renders, and specifically re-checked it after the arrow-glyph fix to prove the fix actually took, not just that the code compiled. ### Phase 9 - hardening

- **Scoped deliberately, not exhaustively.** Concurrency (two identical submissions racing the dedup check's read-then-write) was considered and explicitly deprioritized - a genuine gap, but a narrow race on accidental double-submits isn't worth building for in a 3-4 hour-scoped exercise. What's below is the cheap-and-real subset: guardrails that stop an out-of-scope input from costing money or silently degrading a report, and closing the one failure path that could leave a run stuck with zero explanation.
- **Cost guardrail: `MAX_TRANSCRIPT_LENGTH` (150,000 chars), enforced in `POST /api/runs` before the transcript is hashed, stored, or sent to any API.** Sized off real data, not picked arbitrarily - all 4 reference transcripts run 15,000-65,000 characters, so 150,000 is ~2.3x the largest real one: generous headroom for a genuinely long call, while still catching something that clearly isn't a single call transcript (a pasted document, an accidental multi-paste) before it burns real Stage 1/2 input-token cost. Surfaced client-side too - a live character counter on the home page disables the submit button before the round-trip, rather than only failing after a submit attempt.
- **Quality guardrail: `MIN_TRANSCRIPT_LINES` (5), a different failure mode than length.** A long single-line paste sails past the length checks but breaks something specific: `indexTranscript()` (Phase 2) treats every non-blank line as one speaker turn, so a near-single-line "transcript" collapses most/all evidence citations to the same line number - not a crash, a silently degraded report. Counts non-blank lines the same way `indexTranscript()` does, so this rejects exactly the input shape that would have broken citation, not arbitrary formatting. Both guardrails verified live against the real dev server: a 150,001-character paste, a 50-word single-line paste, and a valid 6-line shape got exactly the expected 400/400/202 responses, with the length counter visibly correct in the browser.
- **Closed the one failure path that wasn't caught anywhere: `failRun()` itself failing.** `POST /api/runs`'s background pipeline already wrapped `runScoringPipeline` in try/catch and called `failRun()` to record why - but `failRun()` is itself a Supabase network call, and if it throws (the same kind of outage that could plausibly have caused the original failure), that became an unhandled rejection inside `after()`, leaving the run row exactly where it was with *nothing* recorded anywhere about why. Now wrapped in its own try/catch; if it also fails, `console.error` puts the run id and both error messages in the server logs, so it's discoverable there even though the DB write itself couldn't happen. Not force-tested live the way Phase 6's "bad model id" failure was (there's no practical way to make Supabase itself fail on demand in this environment) - the fix is verified by code review and the try/catch structure, not a live reproduction; worth being precise about that difference rather than claiming the same proof standard as the rest of the project's bug fixes.
- **The stalled-run backstop (`RUN_STALE_MS`, Phase 6) only checked `status: 'running'`, missing exactly the case the previous bullet creates.** A double-failure (pipeline throws, then `failRun()` also throws) can leave a row on `status: 'pending'` forever if it happens before the very first stage-change write - which the old check didn't cover at all. `GET /api/runs/[id]` now treats `'pending'` the same as `'running'` for staleness. Also fixed the run page's stalled-message copy, which rendered an empty pair of quotes (`It's been on ""...`) whenever `stage` was still `null` - now reads "hasn't started" in that case.
- **Drag-and-drop / "open from folder" file input on the home page**, added after Phase 10 - not a new upload path, just a second way to fill the same `transcript` field the textarea already uses. `FileReader.readAsText` reads the file entirely client-side; nothing is ever uploaded anywhere, so it's exactly as if the same text had been pasted - all the existing guardrails (max length, min lines, the character counter) apply unchanged, no new validation needed. The drop zone wraps the textarea itself (drop anywhere on it, not a separate box), and a hidden `<input type="file">` triggered by an "Open from folder" link covers the click-to-browse case, with the loaded filename shown once picked. Verified the drop path specifically, not just click-to-browse: the Browser pane tooling here has no native OS drag/file-picker simulator, so confirmed the actual code path (not just that it compiles) by dispatching a real `DragEvent` with a constructed `File`/`DataTransfer` and checking the textarea state updated correctly - same mechanism a real OS-level drop triggers, verified end to end rather than assumed from reading the code.
- **Wrong-call-type filename check, catching an easy real mistake: picking the right file but leaving the wrong radio selected.** Loosely matches `kickoff`/`kick-off`/`kick off` and `coach`/`coaching` (case-insensitive) against the loaded filename; if it confidently suggests one type and it disagrees with whichever radio is currently selected, shows an inline warning with a one-click "Switch to X" fix (and a "Keep as Y" dismiss for a genuinely misnamed file). Deliberately says nothing when a filename matches both patterns or neither, rather than guess wrong with false confidence - `call-recording-final.txt` correctly produces no warning at all. Re-evaluated on every render from `detectedType`/`callType` directly rather than tracked as separate state, so switching the radio manually clears the warning for free with no extra reset logic. Verified all 3 paths live: a real mismatch shows the banner and "Switch to Coaching call" correctly flips the radio and clears it; "Keep as X" dismisses without changing the radio; an ambiguous filename shows nothing.
- **A "copy link" button and a much larger PDF download button on the run page.** The copy button is `navigator.clipboard.writeText(window.location.href)` with a 1.8s "Copied!" confirmation and a silent catch on failure (the URL is still right there in the address bar as a fallback) - while verifying it, found that the Claude Code preview browser pane itself denies clipboard-write permission entirely, real user click or not (`NotAllowedError: Write permission denied`), which is an embedding/environment restriction of that specific tool, not a bug - confirmed by isolating it down to exactly that one API call failing with that one error, nothing else. The PDF button is now a big icon-first card (a real `<a href>`, not a JS click handler, so native download behavior - filename, progress, save location - all still work exactly as before) instead of a small text link, since downloading the report is one of this page's two primary actions, not a footnote.
- **"Recent runs" on the home page - deliberately localStorage, not IP or browser-fingerprint tracking.** The actual ask was "close the tab, still see what's going on" without needing to keep the URL around; IP- or fingerprint-based tracking was considered and rejected, because this app has no auth by design (RLS + zero policies, see Phase 6) and multiple people sharing a network/IP would risk one person seeing a different person's run status - a real privacy leak, not hypothetical, given a report can contain identifiable client conversation details. `src/lib/recentRuns.ts` instead remembers submitted run ids in the submitting browser's own `localStorage` only (never sent to the server, no new schema, no cross-device/cross-user reach) - the right trade-off for a no-auth tool. The home page reads that list on mount and fetches each run's LIVE status from the same `GET /api/runs/[id]` the run page itself polls, so it's a real-time view entered from a different page, not a cached snapshot.
  - Populating this list from `useEffect` (not a `useState` lazy initializer) is deliberate, not an oversight - this page is statically prerendered, so there's no `localStorage` at build time; starting empty and filling in after mount is the standard fix for reading browser-only storage without a hydration mismatch, silenced past ESLint's newer `set-state-in-effect` rule with a comment explaining why this specific case is the documented exception, not a suppressed real warning.
  - **Verified end to end for real, including catching my own test-environment noise.** First pass showed a real completed run rendering "Couldn't load" - traced it to my own long-lived debugging browser tab accumulating stale mounts/duplicate requests across many repeated navigations that session (confirmed via `read_network_requests`: a stray 500 on one of several duplicate concurrent requests to the same id), not a real bug - reproduced cleanly in a fresh tab and it was correct every time. Then did the full real loop end to end: filled the actual form, clicked the actual submit button, landed on the real progress page, navigated back to `/`, and watched the new run appear automatically as "⏳ In progress" with zero manual localStorage seeding - the actual feature working exactly as it would for a real user, not a simulated approximation of it.

### Phase 11 - cap-signal evidence gap, closed after external review

- **The gap: an automatic cap fires on a bare model-reported boolean, with no citation of its own.** Per-dimension evidence has been checked against the real transcript since Phase 3; the call-level signals that drive `capEngine.ts` never were - `pipeline/evidenceValidator.ts`'s own comment called this out as "a known gap, documented separately," but it never actually got documented or closed. Flagged independently by an external review of this repo (ChatGPT, asked to review the project before submission) and verified against the actual code before acting on it, not taken on faith: 9 of the 10 automatic caps across both rubrics had zero cross-check, only `nextCallBookedLive`/D10 (Phase 5's bug fix) did, and that one only cross-checks against a paired dimension's evidence - it doesn't validate the signal's own citation.
- **The fix mirrors Phase 3 exactly, applied one layer up.** Stage 1 now reports each cap signal as `{value, quote, line}` instead of a bare boolean - but a citation is only required (and only checked) when `value` is the polarity that would actually fire the cap (`AutomaticCap.firesWhenSignalIs`, already on the rubric contract). The other polarity has no scoring consequence, so holding it to the same bar would be busywork, not safety - the same "no consequence, no need to force evidence" reasoning `capFires()` already applies to a signal that's missing entirely. A cap-firing value with a missing or invalid citation is flipped to the non-firing default and recorded as a `SignalEvidenceIssue` on the Report - visible, not silent, same principle as `cappedBy`/`scoreClampReason`/`SignalCorrection`.
- **Deliberately layered with, not merged into, the existing Phase 5 signal-consistency check** - they catch different failures. This one only asks "is the citation real text at that line" (a fabrication check); Phase 5's `signalConsistency.ts` asks "does this signal agree with its paired dimension's own validated evidence" (a self-contradiction check). A signal can pass this new check (real, unfabricated citation) while still failing Phase 5's (the citation is real but the boolean it's attached to is wrong) - proven live, not just reasoned about, in the verification below.
- **Verified live against the exact Phase 5 bug-story transcript, not a synthetic case.** Ran `coaching-02` fresh: Stage 1 reported `nextCallBookedLive: {value: false, quote: "Okay, booking it now... there, done, it's booked.", line 314}` - a real, exact, unfabricated line from the transcript (confirmed against the source file directly), so Phase 11's new check correctly left it untouched (`signalEvidenceIssues: []`). But the quote is the client confirming a live booking while the signal claims the opposite - exactly Phase 5's contradiction pattern - and `signalConsistency.ts` caught and corrected it exactly as before (`signalCorrections` recorded `nextCallBookedLive` false→true, citing D10's own 5 validated evidence items). D10 scored normally, not zeroed. Two independent layers, two different failure modes, both firing correctly on the same live response without conflicting.
- **Also confirmed the schema/prompt change itself works, not just the downstream logic.** `kickoff-01` (the clean baseline, no caps expected) came back with every signal as `{value: false}` - quote/line correctly omitted for the non-firing polarity, exactly as instructed, confirming Claude follows the new shape rather than just falling back to old habits.

- **7 new unit tests** in `evidenceValidator.test.ts` cover the deterministic part directly: citation validates → trusted, citation missing → flipped + recorded, citation fails validation → flipped + recorded, non-firing value → no citation required, signal never reported → unaffected, `movementCoachingDisabled` (not a cap signal) → untouched. 49/49 passing, typecheck and lint clean.
- **A second external review (same reviewer, second pass on the fresh commit) raised a real follow-up: ~5 of the 10 caps assert something never happened across the WHOLE call** (`noFollowUpQuestionsAnywhere`, `noNorthStarStatement`, `longTermVisionConnected`, `concreteAccountabilityCommitmentPresent`, `noActionStepsEitherParty`) - a single `{line, quote}` citation can't mathematically prove a negative like that, so the worry was that these signals silently get flipped to "cap doesn't fire" whenever the model can't produce a real citation for an unprovable claim, quietly reopening the exact hole this phase closed.
- **Checked it against real live data instead of taking either side on faith.** Re-ran both real cap-firing cases live under this exact code: `kickoff-02`'s `no-north-star` and `coaching-02`'s `no-long-term-vision`. **Both caps still fired correctly** - not silently bypassed, the specific failure mode raised didn't reproduce. In both cases the model provided a real citation (confirmed against the source transcript, not fabricated), so the validator correctly trusted it.
